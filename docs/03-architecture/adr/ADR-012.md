# ADR-012 — WACRM + LangGraph + Tool Gateway/MCP + Model Router + Groq

## Context

The product is evolving from the WACRM WhatsApp/CRM foundation into a governed AI Employee platform. WACRM already provides the operational application layer (WhatsApp, inbox, contacts, conversations, CRM, broadcasts, automations, public API and an MCP server). The platform needs a controlled AI orchestration layer, provider routing, governed tool access and a low-latency model provider without replacing WACRM or creating an uncontrolled autonomous-agent runtime.

## Decision

The canonical runtime architecture is:

```text
WhatsApp / Web
      |
      v
WACRM / Next.js
Inbox + CRM + Contacts + Automations
      |
      v
LangGraph Conversation Runtime
state + bounded orchestration
      |
      +-------------------+--------------------+
      |                   |                    |
      v                   v                    v
Knowledge/RAG       Tool Gateway          Model Router
                          |                    |
                          v                    +--> Groq
                         MCP                   +--> OpenAI
                    + internal tools           +--> Anthropic
                    + external APIs            +--> future local Qwen
      |
      v
Supabase
Postgres + auth + tenant state + knowledge + audit + usage
```

### Component responsibilities

1. **WACRM remains the application foundation.** It owns WhatsApp transport, inbox, CRM, contacts, conversations, broadcasts and deterministic automation.
2. **LangGraph is the bounded orchestration/state layer for AI Employees.** It does not replace WACRM and does not become an unrestricted autonomous control plane.
3. **Tool Gateway is the canonical action boundary.** Every action must be tenant-scoped, permission-checked, auditable and idempotent where applicable.
4. **MCP is an integration protocol behind/alongside the Tool Gateway.** The existing WACRM MCP server is retained and reused; external MCP servers may be added only through the Tool Gateway policy boundary.
5. **Model Router is deterministic software, not an agent.** It selects the provider/model according to tenant configuration, policy, capability and fallback rules.
6. **Groq becomes a supported model provider** in addition to OpenAI and Anthropic. Groq is not the architecture control plane; it is one provider behind the router.
7. **Supabase remains the authoritative data layer** for tenancy, CRM state, AI configuration, knowledge metadata, audit and usage.

## Runtime invariants

- Default AI roles remain exactly two: Conversation Agent and conditional Safety/Quality Supervisor.
- Normal workflow budget remains: simple 1 LLM call, moderate <=2, complex approved <=3.
- No unbounded LangGraph loops.
- Deterministic work stays deterministic.
- Business facts come from authoritative DB/API/tool results, not model invention.
- All tool calls pass tenant authorization and policy checks.
- Provider fallback cannot bypass cost, model allowlist, privacy or data-residency policy.
- MCP tools do not directly receive unrestricted service-role/database access.
- Existing WACRM behavior remains the fallback until the new runtime is explicitly enabled and E2E-verified.

## Implementation strategy

The architecture is introduced incrementally behind controlled boundaries:

1. Model Router + Groq provider adapter.
2. Tool Gateway contract over current internal/public API operations; retain existing MCP server.
3. LangGraph conversation runtime behind a feature flag, initially wrapping one bounded generation path.
4. Add governed tool nodes and structured action proposals.
5. Add conditional Safety/Quality Supervisor only where policy requires it.
6. Activate per workflow only after persistent E2E verification.

## Rejected alternatives

- Replacing WACRM with LangGraph: rejected because orchestration is not an application/CRM transport layer.
- Letting every capability become an agent: rejected because it increases cost, nondeterminism and attack surface.
- Direct model-to-MCP execution without Tool Gateway: rejected because it bypasses canonical authorization/audit/policy controls.
- Groq-only hard binding: rejected to preserve provider neutrality and fallback governance.
- Unbounded ReAct/agent loops: prohibited by the Architecture Constitution and LLM budget.

## Consequences

### Positive

- Reuses the mature WACRM foundation and existing MCP implementation.
- Adds explicit stateful AI orchestration without rebuilding CRM/WhatsApp.
- Provider-neutral design with Groq for low-latency inference.
- Clear control point for tools, security, audit and cost.
- Allows future local Qwen or other providers without redesigning the product.

### Costs / risks

- Adds LangGraph dependency and runtime complexity.
- Requires strict state schemas, timeouts, cancellation and call-budget enforcement.
- MCP/external tool reliability must be isolated from the WhatsApp acknowledgment path.
- Groq model availability/quotas can change, therefore provider/model selection must stay configurable.

## Acceptance criteria

This ADR is implemented only when code + migrations + tests demonstrate:

- Groq is accepted, validated and callable through the canonical Model Router.
- Existing OpenAI/Anthropic behavior remains functional.
- WACRM MCP remains available and tenant/API-key scoped.
- Tool Gateway exposes an explicit permission/audit contract.
- LangGraph runtime has bounded graph topology and hard LLM-call budget enforcement.
- New runtime is disabled by default until E2E evidence is recorded.
