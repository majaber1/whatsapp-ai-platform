# ADR-011 — Open-Source Composition Strategy

## Context

The product requires a mature official WhatsApp/CRM foundation plus a governed AI Employee model. Rebuilding messaging, inbox, CRM, employee lifecycle, skills, evidence, permissions, memory, provider abstraction and development-governance patterns entirely from zero would add delivery risk without differentiating the product. Conversely, blindly combining multiple independent repositories would create incompatible runtimes, duplicated auth/data models, uncontrolled agents, upgrade risk and conflicting development conventions.

## Decision

Build **one WhatsApp AI Platform repository and one canonical product architecture**. External open-source projects are assigned explicit roles and adoption boundaries. No upstream project is allowed to redefine the canonical tenancy, security, AI-runtime or data architecture by itself.

### 1. WACRM — application foundation

Pinned upstream: `ArnasDon/wacrm@98b5bd26e8feacacfd4b74ff58411acb8154d212` (MIT).

Use as the preferred application foundation for architecture-compatible portions of:

- official Meta WhatsApp Cloud API connectivity
- webhook verification/signature/security primitives
- inbound/outbound messaging
- inbox/conversations
- contacts/tags/custom fields
- CRM/pipeline
- templates/broadcasts
- flows/basic automations
- account/RLS groundwork
- public API/MCP groundwork

WACRM is a foundation, not the final product definition. Its current tenancy, AI and product assumptions must be evaluated against our target architecture.

### 2. CrewClaw — AI Employee governance model

Pinned upstream: `staruhub/CrewClaw@9e456e51064580bab3206d0e837018cfafdb7962` (Apache-2.0).

Selectively adapt architecture-compatible concepts/components for:

- AI Employee contract/profile
- permissions and capability boundaries
- Doctor/preflight checks
- bounded task execution metadata
- evidence/artifact capture
- approval gates
- task events
- KPI/performance derived from evidence
- employee lifecycle and package/registry concepts

Do not make CrewClaw's full runtime the platform control plane in v1 without a separate ADR.

### 3. OpenHire — employee skills/workforce/memory model

Pinned upstream: `pzy2000/OpenHire@17842144d0efc2f0661c00bb28b38d62ba331199` (MIT).

Selectively adapt architecture-compatible concepts/components for:

- employee registry
- skill catalog
- reusable cases
- employee workspace/configuration
- long-term memory lifecycle with versioning/rollback concepts
- provider abstraction concepts
- admin/runtime observability concepts

Do not adopt OpenHire's multi-worker/control-agent orchestration or high tool-iteration defaults as our normal runtime.

### 4. Goose — selective runtime/provider/MCP reference

Canonical reviewed upstream: `aaif-goose/goose@5e90925962f05acf8e255032de44d16c4a7768a2` (Apache-2.0).

The originally surfaced `ArnasDon/goose` repository states that Goose moved to the Agentic AI Foundation under the Linux Foundation. Therefore the canonical AAIF repository is the reviewed source for future adaptation rather than the older mirror/import.

Evaluate and selectively adapt architecture-compatible patterns/components for:

- provider-neutral model integration
- provider configuration/validation patterns
- MCP extension/connectivity patterns
- tool execution lifecycle
- diagnostics and runtime observability
- extension packaging and capability discovery
- local/self-hosted provider compatibility where useful

Goose is **not** adopted as the canonical WhatsApp AI Employee runtime in v1. It must not introduce unrestricted autonomous loops, bypass the Tool Gateway, bypass tenant authorization, or override the platform's LLM-call budgets. Any direct embedding of a Goose runtime component requires a separate implementation fit-gap review and, if material, an ADR/CR.

### 5. Agentic Coding Starter Kit — development governance/tooling only

Pinned reviewed upstream: `leonvanzyl/agentic-coding-starter-kit@08bce5d393a7b20c7fdb3bde488cc90a343eec15` (MIT).

Adopt selected **development-process** patterns, not its application stack:

- `AGENTS.md` / `CLAUDE.md` agent instructions
- spec-first workflow for large/risky features
- resumable implementation waves
- scoped task files and dependency ordering
- implementation/review/security/UI/shipping skills where compatible
- agent context splitting and controlled sub-agent usage
- verification gates such as lint, typecheck, test and build

Do **not** import its Better Auth, Drizzle/PostgreSQL scaffold, application database model, starter UI, storage stack or OpenRouter application setup into the WACRM-based product solely because the starter includes them. Our existing Supabase/Postgres/RLS application foundation remains authoritative unless changed through architecture governance.

The Universal Project Governance Architecture & Delivery Standard remains authoritative over all imported agent instructions or skills. Starter-kit instructions may strengthen execution but may not weaken Definition of Ready, Definition of Done, architecture freeze, live E2E or change-control requirements.

### 6. Our canonical controlled core

The following remain owned by the WhatsApp AI Platform architecture:

- true SaaS tenancy and memberships
- canonical database/domain model
- multi-number WhatsApp ownership model
- canonical provider-message identity
- AI Employee schema/versioning
- shared Conversation Agent runtime
- conditional Safety/Quality Supervisor
- deterministic workflow/router/policy/authorization layers
- Tool Gateway and Integration Gateway
- model routing and LLM budgets
- knowledge/RAG governance and provenance
- usage/cost metering and billing
- Saudi/Arabic behavior and local integrations
- AI evaluation and audit trail
- enterprise admin and governance dashboard
- security/compliance controls
- unified UX and API contracts

## Runtime invariant

An AI Employee is primarily a **governed, versioned configuration over a shared runtime**. It is not automatically an independent autonomous LLM process.

Default runtime roles remain:

1. Conversation Agent — primary reasoning/response role.
2. Safety/Quality Supervisor — conditional role for risk, low confidence, sensitive/high-impact actions or policy review.

Router, RAG, memory storage, authorization, workflow engine, tool executor, provider gateway and deterministic validation are software components, not separate LLM agents.

Default budget:

- simple workflow: 1 LLM call
- moderate workflow: ≤2 LLM calls
- complex approved workflow: ≤3 LLM calls

No unlimited agent loops.

## Repository strategy

Use one controlled repository: `majaber1/whatsapp-ai-platform`.

- WACRM is the imported application foundation at the pinned baseline.
- Do not vendor entire CrewClaw, OpenHire, Goose or Agentic Coding Starter Kit repositories by default.
- Selectively port only approved code, schemas, skills or patterns; record exact source-file provenance if copied.
- Keep `upstreams.lock.json` authoritative for reviewed upstream versions.
- Upstream upgrades require compatibility/security/license review and formal change control when material.
- Development tooling must never silently modify application architecture.

## Consequences

### Benefits

- substantial reduction in commodity WhatsApp/CRM build work
- faster delivery of the differentiated AI Employee layer
- formal employee-governance concepts without inventing everything ourselves
- provider/MCP/runtime patterns available without committing to another full control plane
- stronger coding-agent execution discipline without replacing our application stack
- lower risk than merging multiple full runtimes
- retained control over tenancy, AI spend, security and product evolution

### Costs/Risks

- WACRM must be adapted for our target multi-tenant SaaS model
- selective ports require provenance tracking
- upstream divergence requires deliberate upgrade work
- Goose/CrewClaw/OpenHire are not authoritative product architecture
- agent-development skills can create process noise if imported indiscriminately; only selected governed skills should be adopted

## Compliance

Any implementation that introduces a different primary WhatsApp foundation, full third-party agent runtime, unrestricted multi-agent loop, competing application database/auth stack, or alternative tenancy model requires a new ADR/CR.
