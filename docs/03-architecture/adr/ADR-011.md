# ADR-011 — Open-Source Composition Strategy

## Context

The product requires a mature official WhatsApp/CRM foundation plus a governed AI Employee model. Rebuilding messaging, inbox, CRM, employee lifecycle, skills, evidence, permissions, and memory patterns entirely from zero would add delivery risk without differentiating the product. Conversely, blindly combining three independent repositories would create incompatible runtimes, duplicated auth/data models, uncontrolled agents, and upgrade risk.

## Decision

Build **one WhatsApp AI Platform repository and one canonical product architecture** with the following source-composition boundaries.

### 1. WACRM — application foundation

Pinned upstream: `ArnasDon/wacrm@98b5bd26e8feacacfd4b74ff58411acb8154d212` (MIT).

Use as the preferred application foundation for architecture-compatible portions of:

- official Meta WhatsApp Cloud API connectivity
- webhook verification/signature/security primitives
- inbound/outbound messaging
- inbox/conversations
- contacts/tags/custom fields
- CRM/pipeline
- templates/broadcasts
- flows/basic automations
- account/RLS groundwork
- public API/MCP groundwork

WACRM is a foundation, not the final product definition. Its current tenancy, AI and product assumptions must be evaluated against our target architecture.

### 2. CrewClaw — employee governance model

Pinned upstream: `staruhub/CrewClaw@9e456e51064580bab3206d0e837018cfafdb7962` (Apache-2.0).

Selectively adapt architecture-compatible concepts/components for:

- AI Employee contract/profile
- permissions and capability boundaries
- Doctor/preflight checks
- bounded task execution metadata
- evidence/artifact capture
- approval gates
- task events
- KPI/performance derived from evidence
- employee lifecycle and package/registry concepts

Do not make CrewClaw's full beta runtime the platform control plane in v1 without a separate ADR.

### 3. OpenHire — employee skills/workforce/memory model

Pinned upstream: `pzy2000/OpenHire@17842144d0efc2f0661c00bb28b38d62ba331199` (MIT).

Selectively adapt architecture-compatible concepts/components for:

- employee registry
- skill catalog
- reusable cases
- employee workspace/configuration
- long-term memory lifecycle with versioning/rollback concepts
- provider abstraction concepts
- admin/runtime observability concepts

Do not adopt OpenHire's multi-worker/control-agent orchestration or high tool-iteration defaults as our normal runtime.

### 4. Our canonical controlled core

The following remain owned by the WhatsApp AI Platform architecture:

- true SaaS tenancy and memberships
- canonical database/domain model
- AI Employee schema/versioning
- shared Conversation Agent runtime
- conditional Safety/Quality Supervisor
- deterministic workflow/router/policy/authorization layers
- Tool Gateway and Integration Gateway
- model routing and LLM budgets
- knowledge/RAG governance
- usage/cost metering and billing
- Saudi/Arabic behavior and local integrations
- AI evaluation and audit trail
- enterprise admin and governance dashboard
- security/compliance controls
- unified UX and API contracts

## Runtime invariant

An AI Employee is primarily a **governed, versioned configuration over a shared runtime**. It is not automatically an independent autonomous LLM process.

Default runtime roles remain:

1. Conversation Agent — primary reasoning/response role.
2. Safety/Quality Supervisor — conditional role for risk, low confidence, sensitive/high-impact actions or policy review.

Router, RAG, memory storage, authorization, workflow engine, tool executor and deterministic validation are software components, not LLM agents.

Default budget:

- simple workflow: 1 LLM call
- moderate workflow: ≤2 LLM calls
- complex approved workflow: ≤3 LLM calls

No unlimited agent loops.

## Repository strategy

Use one new controlled repository: `whatsapp-ai-platform`.

- Import/fork WACRM source at the pinned commit as the application foundation after source-acquisition audit.
- Do not vendor entire CrewClaw/OpenHire repositories by default.
- Selectively port only approved code or schemas/components; record exact source-file provenance if/when copied.
- Keep `upstreams.lock.json` authoritative for reviewed upstream versions.
- Upstream upgrades require compatibility/security/license review and formal change control when material.

## Consequences

### Benefits

- substantial reduction in commodity WhatsApp/CRM build work
- faster delivery of the differentiated AI Employee layer
- formal employee-governance concepts without inventing everything ourselves
- lower risk than merging three full runtimes
- retained control over tenancy, AI spend, security and product evolution

### Costs/Risks

- WACRM must be adapted for our target multi-tenant SaaS model
- selective ports require provenance tracking
- upstream divergence will require deliberate upgrade work
- CrewClaw/OpenHire are not treated as authoritative product architecture

## Compliance

Any implementation that introduces a different primary WhatsApp foundation, full third-party agent runtime, uncontrolled multi-agent loop, or alternative tenancy model requires a new ADR/CR.
